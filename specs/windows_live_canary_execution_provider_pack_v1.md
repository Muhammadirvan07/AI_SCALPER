# Windows LIVE Canary Execution Provider Pack v1

**Author:** Codex with AI_SCALPER project owner
**Date:** 2026-07-29
**Status:** Approved for implementation
**Reviewers:** senior architecture, security, ship-gate
**Target:** Windows XM LIVE canary Execution provider overlay

## Context

AI_SCALPER has a frozen Windows Execution provider-pack v1 for `DEMO` and
dormant `DEMO_AUTO`, plus a separate source-level Windows LIVE materializer.
The LIVE materializer validates an exact 49-port contract and remains unable
to run while the checked-in central LIVE policy is disabled. It is not yet
available through the deterministic Windows release flow: no exact generated
provider overlay binds the materializer to an atomic Execution base release.

This feature adds an additive, offline LIVE provider-pack profile. It reuses
the existing four-file overlay shape and atomic-suite Execution role, but uses
new LIVE-only schemas, identities, credential purpose, generated imports, and
validation APIs. The existing v1 generator, parser, generated bytes, contract
set, and public names remain unchanged. Pack generation and validation are
static release operations; they do not import the generated provider or
materialize runtime state.

The checked-in central lock stays false. A valid pack is only source evidence
for the next configured-candidate and external Windows conformance milestones.
It is not a launch session, credential, provider acceptance, task definition,
order authority, or broker capability.

## Functional Requirements

- FR-1: The implementation MUST add separate LIVE pack input, configuration,
  validation, identity, and implementation schemas without changing any
  version-1 provider-pack constant, parser, function, or generated output.
- FR-2: The LIVE pack MUST contain exactly four files:
  `config/windows_service_config.json`,
  `configured_providers/__init__.py`,
  `configured_providers/execution_provider.py`, and
  `reviewed_windows_factory.py`.
- FR-3: The generated provider module MUST embed exactly one canonical,
  non-secret LIVE provider configuration and import only
  `json` plus the two public parsing/materialization functions from
  `live_runtime.windows_live_canary_execution_provider`.
- FR-4: The generated factory MUST import only the generated Execution
  provider bridge and expose one `build(runtime_config, context)` function.
- FR-5: The pack MUST bind exactly 49 ordered provider roles, 40 required
  roles, nine forbidden cross-mode roles, and exactly 12 ordered credential
  purposes beginning with `MT5_LIVE_SESSION`.
- FR-6: Each generated provider binding MUST bind its exact LIVE contract
  hash, provider kind, purpose-matched credential reference, configuration
  hash, and an implementation hash derived from the exact ordered foundation
  inventory.
- FR-7: The exact foundation inventory MUST include
  `live_runtime/windows_live_canary_execution_provider.py`,
  `live_runtime/windows_execution_provider_pack.py`, and
  `live_runtime/windows_provider_primitives.py` from the verified atomic-suite
  Execution archive. Each byte MUST also match the local reviewed source.
- FR-8: The Execution service allowlist MUST include the dormant LIVE
  materializer and its imports. The configured-release tooling allowlist MUST
  include only the offline LIVE pack CLIs required to generate and validate
  the pack. No dependency package may be added.
- FR-9: Pack input MUST contain only the LIVE provider core and the exact
  bounded service configuration. It MUST NOT accept caller-provided suite,
  base-release, service-file, provider-binding, implementation, or pack
  identity hashes.
- FR-10: Generation MUST derive suite identity, Execution base identity,
  service-config hash, provider bindings, foundation hashes, and pack identity
  from exact verified bytes.
- FR-11: Static parsing MUST require `runtime_mode=LIVE`, the LIVE schema and
  credential target prefix, exact canonical lowercase non-zero hashes, exact
  provider/credential ordering, a distinct clock trust domain, an absolute
  local Windows clock path, and all deny-only safety values.
- FR-12: Pack generation and validation MUST statically parse Python with AST,
  reject dynamic imports/evaluation and forbidden import drift, and MUST NOT
  import the generated provider or factory.
- FR-13: Two generations from identical canonical input and identical suite
  bytes MUST create byte-identical files and the same pack identity.
- FR-14: Output creation MUST be exclusive. Failure after ownership is
  established MUST remove only the exact invocation-owned files/root and MUST
  not overwrite or remove a replacement path.
- FR-15: Validation MUST independently reconstruct every generated byte,
  provider binding, foundation hash, service hash, suite/base binding, and
  pack identity from the supplied pack and atomic suite.
- FR-16: Input, generated source, output, result, CLI output, and errors MUST
  contain no credential value, account login, password, token, private key,
  permit, environment arm, launch session, or broker payload.
- FR-17: Generation and validation MUST NOT read credentials, call providers,
  open SQLite, use network, start a process, install a task, import/initialize
  MT5, issue or consume authority, call `order_check`/`order_send`, or mutate a
  broker.
- FR-18: Every successful result MUST retain `provider_accepted=false`,
  `provider_materialized=false`, `production_execution_ready=false`,
  `live_allowed=false`, `safe_to_demo_auto_order=false`,
  `promotion_eligible=false`, `order_capability=DISABLED`, and `max_lot=0.01`.
- FR-19: The CLI MUST expose only suite root, Execution base release, pack
  input, and output root for preparation; validation exposes only suite root,
  Execution base release, and pack root.
- FR-20: Success status MUST be
  `EXTERNAL_LIVE_PROVIDER_ACCEPTANCE_REQUIRED`; it MUST NOT claim configured
  candidate completion, Windows acceptance, demo-auto readiness, LIVE
  readiness, or production readiness.

## Non-Functional Requirements

- NFR-1: All failures MUST use stable uppercase non-secret reason codes and
  unavailable evidence MUST fail closed.
- NFR-2: Canonical JSON MUST be UTF-8, sorted, compact, newline-terminated;
  duplicate keys and non-finite values MUST be rejected.
- NFR-3: Each input/output file MUST be at most 4 MiB, total pack bytes at
  most 16 MiB, and the base archive at most 256 MiB. Collections MUST be
  bounded before per-item work.
- NFR-4: Symlink/reparse members, unstable reads, unknown files/directories,
  case collisions, path traversal, secret patterns, and sensitive JSON keys
  MUST fail closed.
- NFR-5: Security behavior MUST be identical in normal Python and
  `PYTHONOPTIMIZE=2`; no security decision may rely on `assert`.
- NFR-6: The implementation MUST use only standard-library and already locked
  first-party dependencies and MUST pass dependency/import closure checks.
- NFR-7: Focused tests MUST complete with effect sentinels untouched and MUST
  cover deterministic rebuild, tamper, foundation drift, input drift, cleanup,
  CLI surface, and exact V1 compatibility.
- NFR-8: The complete normal and optimized Python suites, Ruff, compile,
  dependency-lock verification, scoped diff checks, release builders, and
  project ship gate MUST be rerun before source commit.

## Acceptance Criteria

### AC-1: Exact deterministic pack (FR-2, FR-3, FR-4, FR-13)

Given one exact atomic base suite and canonical LIVE pack input
When two independent pack preparations run
Then both contain the exact same four files and identical bytes
And both return the same non-zero pack identity.

### AC-2: Exact LIVE inventory (FR-5, FR-6, FR-11)

Given a generated pack
When its embedded configuration is statically extracted
Then it contains exactly 49 ordered provider bindings and 12 ordered
credential references
And every contract, kind, credential purpose, configuration hash, and
implementation hash is reconstructed from reviewed inputs.

### AC-3: Exact foundation closure (FR-7, FR-8, FR-10)

Given the exact atomic-suite Execution archive
When LIVE pack preparation or validation runs
Then all three foundation members exist in the archive and match local source
bytes
And missing, extra, or drifted foundation bytes fail before output.

### AC-4: Pure static validation (FR-12, FR-16, FR-17)

Given import, credential, provider, SQLite, network, process, task, MT5, and
broker effect sentinels
When input parsing, pack generation, and pack validation run
Then the generated provider is never imported and every sentinel remains
untouched.

### AC-5: Tamper and schema rejection (FR-9, FR-11, FR-15, NFR-2, NFR-4)

Given a duplicate key, unknown field, reordered entry, wrong schema/mode,
credential drift, contract drift, service hash drift, source tamper, extra
file, symlink, or noncanonical JSON
When preparation or validation runs
Then it fails with a stable reason code and publishes no valid result.

### AC-6: Transactional output custody (FR-14)

Given an existing destination, a mid-write failure, or replacement of an
invocation-owned root
When preparation fails
Then no pre-existing byte is overwritten
And cleanup removes only bytes whose exact owned identity still matches.

### AC-7: V1 compatibility (FR-1)

Given all pre-existing Windows Execution provider pack tests and canonical
V1 contract hash
When the additive LIVE APIs and CLIs are present
Then every V1 test passes unchanged and the V1 46-port contract-set hash
remains `0003087efd10ade71255d6e05db45060febac9f98b50a0d29c1a7212d55db148`.

### AC-8: Deny-only CLI result (FR-18, FR-19, FR-20)

Given a valid LIVE pack input
When prepare and validate CLIs complete
Then output reports exactly 49 providers, 12 credential references, zero
runtime/broker effects, disabled order capability, false production readiness,
and `EXTERNAL_LIVE_PROVIDER_ACCEPTANCE_REQUIRED`.

### AC-9: Release closure (FR-8, NFR-6, NFR-8)

Given a clean reviewed commit
When Execution and configured-tooling release builders run
Then import closure contains the LIVE materializer and both offline CLIs in
their intended bundles only
And all safety fields remain unchanged.

### AC-10: Honest ship gate (FR-20)

Given all local acceptance criteria pass
When project status is updated
Then only the deterministic LIVE provider-pack slice is marked locally
complete, while configured candidate, external Windows/XM acceptance,
central unlock, demo soak, and first broker canary remain blocked.

## Edge Cases

- EC-1: An Execution base archive from another suite or role MUST fail before
  reading pack input.
- EC-2: A base archive missing the LIVE materializer or containing locally
  drifted foundation bytes MUST fail before output-root creation.
- EC-3: An input that supplies derived suite, release, service, binding, or
  identity fields MUST fail as an unknown-field schema violation.
- EC-4: `MT5_DEMO_SESSION`, a reused credential identity/fingerprint, or clock
  trust collision MUST fail static parsing.
- EC-5: A 48/50-entry provider list, reordered role, wrong kind/contract,
  credential on a non-credential role, or credential omission MUST fail.
- EC-6: A generated provider import change, extra assignment, dynamic import,
  `eval`, `exec`, `compile`, or `__import__` MUST fail validation.
- EC-7: `MetaTrader5`, `order_check`, `order_send`, subprocess, network, or
  task APIs appearing in generated output MUST fail static validation.
- EC-8: An existing empty or populated output root, file, symlink, or reparse
  path MUST be preserved and rejected.
- EC-9: An interrupted partial pack without all exact members MUST fail
  independent validation.
- EC-10: A replacement path that takes the original output name during cleanup
  MUST remain untouched.
- EC-11: Normal and optimized mode MUST return the same result/reason code for
  every valid and invalid fixture.
- EC-12: Presence of a valid pack while the central LIVE lock is false MUST
  not create runtime authority; pack status remains external-acceptance
  required.

## API Contracts

No HTTP, broker, credential, scheduler, activation, or order API is added.
The only new public APIs are offline filesystem preparation/validation:

`GET /not-applicable` is a documentation-only marker and MUST NOT be
implemented.

```typescript
interface WindowsLiveCanaryExecutionProviderPackValidation {
  readonly packId: string;
  readonly packIdentitySha256: string;
  readonly providerCount: 49;
  readonly credentialReferenceCount: 12;
  readonly status: "EXTERNAL_LIVE_PROVIDER_ACCEPTANCE_REQUIRED";
  readonly providerAccepted: false;
  readonly providerMaterialized: false;
  readonly productionExecutionReady: false;
  readonly liveAllowed: false;
  readonly orderCapability: "DISABLED";
}
```

```python
    ...
```

Preparation CLI:


## Data Models

| Model | Field | Type | Constraints |
|---|---|---|---|
| LIVE pack input | `schema_version` | string | Exact LIVE pack input v1 schema |
| LIVE pack input | `provider_configuration` | object | Non-secret core only; derived bindings forbidden |
| LIVE pack input | `service_config` | object | Exact bounded service fields |
| Static LIVE configuration | `provider_bindings` | tuple[49] | Exact LIVE order, contracts, custody, foundation hashes |
| Static LIVE configuration | `credential_references` | tuple[12] | Exact LIVE purposes and distinct reference/key/target/fingerprint |
| LIVE pack validation | identities | SHA-256 | Exact suite/base/config/service/files/pack bindings |
| LIVE pack validation | effects | booleans | All false |
| LIVE pack validation | safety | fields | Disabled, deny-only, max lot 0.01 |

## Out of Scope

- OS-1: Enabling `execution_policy.LIVE_ALLOWED` or changing any central
  execution-policy value.
- OS-2: Building the suite-bound configured LIVE candidate, source-bound
  candidate, Task Scheduler definition, installer, launcher attestation, or
  provider-conformance packet.
- OS-3: Implementing or provisioning concrete credential, clock, WORM/CAS,
  risk, reconciliation, news, Decision IPC, heartbeat, MT5, or broker ports.
- OS-4: Importing the generated provider, materializing a factory, starting a
  Windows task/service, initializing MT5, reading an account, or sending an
  order.
- OS-5: Treating local tests or deterministic bytes as XM evidence, demo-auto
  soak evidence, LIVE approval, broker acceptance, or production readiness.
- OS-6: Claiming the project is 100% complete or safe for unrestricted live
  trading.
